# CSS-14 portable installation identity v1

No local database migration or service route is introduced. Local creation is
explicit: an authorized backend workflow may call
`scanner.security.community_identity.load_or_create_installation_identity(data_dir)`
when enabling community access. Ordinary application startup, package upgrade,
restore, and the signing helpers do **not** call this function or rotate keys.
It takes the caller's configured runtime data directory, not the working
directory, container image or cache. A complete absence at that location is
a new installation; CSS-21 must check its own persisted contributor records
before invoking creation so loss of **all** external identity files cannot
silently become a new identity. An incomplete existing identity is never
regenerated by this loader.

## Private-file inventory

Under `${data_dir}/secrets/community/`:

| File | Full and settings/identity backups, plain or encrypted | Meaning |
| --- | --- | --- |
| `identity.json` | Include | Versioned installation ID, public key and key ID, nullable service URL and contributor ID, last-known key state, nullable pending replacement descriptor |
| `current.key` | Include | Canonical standard padded base64 of 32 raw Ed25519 private-key seed bytes followed by LF; never log, return from settings APIs, or serve to a browser |
| `pending.key` | Include **only when the manifest records a pending replacement** | Same private-key encoding for the single pending operation; not activated by startup or backup restore |
| `identity.lock` | Exclude | Persistent kernel-lock file; re-create at the target, never use an archived lock |

`community-identity-1` is the exact manifest `schema_version`. Other fields
are `installation_id` (canonical random UUID), `key_id`, `public_key`
(canonical standard padded base64 of the raw 32-byte public key),
`contributor_id`, `service_url`, `last_known_key_state`, and
`pending_replacement`. Fresh keys have null contributor and service values,
`unenrolled` state and null pending replacement. Enrolled local state can
record `active`, `retired`, `revoked`, or `compromised`, but this value is a
**last-known hint**; CSS-25/29 must check authoritative service status before
any protected action. The public `key_id` is `sha256:` plus 64 lowercase
hex digits of SHA-256 over the **raw Ed25519 public bytes**. The manifest
is strictly parsed (unknown version/fields, duplicate fields, wrong key ID,
invalid public/private pair and unsafe files fail closed). A pending
descriptor stores `operation_id`, `key_id`, and `public_key`; its matching
`pending.key` is required. No private material appears in the manifest.

The identity directory and created files are owner-only (`0700` directories,
`0600` files on POSIX). Existing key files with broader permissions, symlinks,
nonregular files and mismatched keypairs are refused, not repaired in place.
The filesystem interprocess lock also serializes threads; the same runtime
maintenance lock primitives support POSIX and Windows. Windows storage uses
the existing per-user AppData ACL model, with the chosen runtime data directory
required to remain private; native Windows ACL inspection remains a platform
validation step. Temp files are private, flushed and atomically renamed, then
the directory is synced where supported. The public manifest is published
**before** the current key: a crash between the two leaves a nonempty,
incomplete identity, not a second key. For explicit replacement staging,
`pending.key` is published **before** the manifest names it; an interrupted
stage is also incomplete, never silently restarted or automatically rotated.

`IdentityUnavailable.status` distinguishes `incomplete`, `corrupt`,
`unavailable` and `pending`. Restore the matched manifest and key from an
appropriate backup or use the future explicit, Discord-authorized recovery UI;
never delete a suspicious file to force new enrollment. The helper
`save_identity_registration` records a verified enrollment response while
keeping the key/installation stable. `stage_identity_replacement(data_dir,
operation_id=...)` reserves one key under the existing lock only when
explicitly called by a future UI-authorized rotation path; retries of the
same operation return the same pending key and a different operation is
rejected. It never activates or retires a key; CSS-32 reconciles that with
the authoritative server. No endpoint or independent CLI rotation command
is added here.

`read_identity_backup_snapshot(data_dir)` validates under the same lock and
returns immutable copies of the explicit file allowlist above, with secret
bytes excluded from object representation. CSS-16 includes these bytes
inside the archive for both backup kinds, encrypting only when selected (off by
default under updated D06). Both modes restore/check them together with
the local state, and verify the public/private pairing before activation.
The call does not create or publish a replacement. CSS-21/29 must keep
pending operations and service identifiers consistent with this generation;
neither a database-only copy nor a private-file-only copy is an identity
backup. CSRF credentials and other secrets have separate inventories.

Tests use temporary runtime directories, synthetic keys and process/thread
contention; no live service, user database, or personal key file is touched.
